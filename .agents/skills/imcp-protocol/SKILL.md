# IMCP プロトコル仕様

このスキルは、IMCP のフレーム形式、アドレス体系、トランザクション、状態遷移、エラー回復をプロトコルの観点だけで扱う。回答では、ワイヤ上のバイト列とスタッフィング解除後の論理値を区別し、規定されている動作と未規定の動作を分けて説明する。

## 基本定数

| 名前 | 値 | 役割 |
| --- | --- | --- |
| `SOF` | `0xFE` | フレーム開始。フレーム境界ではエスケープしない |
| `EOF` | `0xFF` | フレーム終了。フレーム境界ではエスケープしない |
| `ESC` | `0xFD` | フレーム内部の予約バイトをスタッフィングする印 |
| `ESC_XOR` | `0x20` | 予約バイトの変換に使う XOR 値 |
| 最大ペイロード長 | `128` bytes | `Data` と `Set` の最大論理ペイロード長 |

## フレーム形式

ワイヤ上の順序は次のとおり。

```text
SOF | To | From | Type | Payload Length (LE) | Payload | Checksum | EOF
```

- `SOF` と `EOF` は各 1 byte で、フレーム境界としてそのまま送る。
- `To`、`From`、`Type`、`Payload Length`、`Payload`、`Checksum` はフレーム内部の論理フィールドである。
- ヘッダーは `To` 1 byte、`From` 1 byte、`Type` 1 byte、`Payload Length` 2 bytes の合計 5 bytes。
- ペイロード長はスタッフィング解除後のペイロード長を unsigned 16-bit little-endian で表す。
- 最小の論理フレーム内部長はヘッダー 5 bytes + チェックサム 1 byte = 6 bytes。
- 最大の論理フレーム内部長は `5 + 128 + 1 = 134` bytes。全ての内部 byte がスタッフィングされる上限を含めた最大ワイヤ長は `2 + 134 * 2 = 270` bytes。

### チェックサム

チェックサムは、スタッフィング前の `To` からペイロード末尾までを XOR した 1 byte である。

```text
Checksum = To ^ From ^ Type ^ LengthLo ^ LengthHi ^ Payload[0] ^ ... ^ Payload[n-1]
```

`SOF`、`EOF`、チェックサム自身は計算対象に含めない。受信時は長さを検証した後、スタッフィング解除済みの論理 byte 列で XOR を再計算する。

## スタッフィングと再同期

フレーム内部で `SOF`、`EOF`、`ESC` を表す場合だけ、次の変換を行う。

| 論理 byte | ワイヤ上の 2 bytes |
| --- | --- |
| `0xFE` (`SOF`) | `0xFD 0xDE` |
| `0xFF` (`EOF`) | `0xFD 0xDF` |
| `0xFD` (`ESC`) | `0xFD 0xDD` |

- フレーム内部の予約 byte は必ず `ESC` と変換後 byte の組にする。
- `ESC` の直後に有効なのは `0xDE`、`0xDF`、`0xDD` の 3 種類だけである。その他の byte は不正なエスケープシーケンスとする。
- `ESC` だけで入力が終わった場合は未完成フレームであり、次の入力を待つ。
- フレーム外の byte は次の `SOF` まで無視する。
- 受信中にエスケープされていない `SOF` が現れた場合、途中のフレームを破棄し、その `SOF` から新しいフレームを開始する。
- 不正なエスケープシーケンスやバッファ長超過が発生した場合、破損したフレームを破棄する。後続に `SOF` があればそこから再同期する。
- `EOF` はエスケープされていない場合だけ終端と解釈する。終端で論理フレームを検証し、チェックサム・長さ・種別・ペイロード形状のいずれかが不正ならそのフレームを拒否する。

## アドレス体系

| 値 | 意味 | 用途 |
| --- | --- | --- |
| `0x00` | 未割り当て | Join の送信元、SetAddress の送信先 |
| `0x01` | Master | 割り当て管理と通常の制御元 |
| `0x02`–`0xFE` | 割り当て済みユニキャスト | クライアントの通常アドレス |
| `0xFF` | Broadcast | 全ノード宛て |

- `0x00`、`0x01`、`0xFF` はクライアントへの割り当て先にしてはならない。
- Join は未割り当てアドレスから Master (`0x01`) へ送る。
- SetAddress は Master (`0x01`) から未割り当てアドレス (`0x00`) へ送る。割り当て後も同じフレームを再送できるよう、Ready 状態の対象クライアントは内容が一致する SetAddress を受け付ける。
- 宛先が自分のユニキャストでも Broadcast でもないフレームは、破損ではなく対象外のフレームとして無視する。

## フレーム種別とペイロード

| Type | 論理ペイロード | 長さ | 意味 |
| ---: | --- | ---: | --- |
| `0` | なし | `0` | Ping。受信側は Pong を返す |
| `1` | なし | `0` | Pong |
| `2` | ACK の対象宛先 byte | `1` | 受信した処理の確認 |
| `3` | `id: u32` little-endian | `4` | Join 要求 |
| `4` | `address: u8` + `id: u32` little-endian | `5` | アドレス割り当て |
| `5` | 任意の byte 列 | `0`–`128` | Data |
| `6` | 任意の byte 列 | `0`–`128` | Set。通常の要求として ACK 対象 |

固定長種別では、ペイロード長が表の値と一致しなければならない。`Data` と `Set` の長さは最大 128 bytes で、ヘッダーの長さは常にスタッフィング前の値を示す。

## ACK とトランザクション

- ユニキャストの `Set` を受信した側は、送信元へ `Ack(original destination)` を返す。
- Broadcast の `Set` に対する ACK のペイロードは `0xFF`。複数ノードが応答し得るため、送信側は Broadcast ACK を個別の宛先確認と解釈しない。
- SetAddress の送信先は `0x00` なので、割り当てを受けたクライアントの ACK は `Ack(0x00)` になる。ACK の送信元は割り当て後のクライアントアドレスである。
- SetAddress の再送で同じ ACK が複数回届くことは正当である。Master が既に保留を解消した後の重複 `Ack(0x00)` は、処理済みの確認として冪等に扱う。
- Ping には ACK ではなく Pong を返す。
- Join は通常の ACK を返さず、Master が SetAddress を送ることで割り当てトランザクションを進める。
- Master が処理中に保持できるアドレス割り当ては 1 件で、別の Join は保留中の処理を妨げない。保留中の Join と同じ `id` の再送は同じ割り当て要求の再送として扱う。
- 現行の割り当てトランザクションでは、SetAddress の送信試行は最大 3 回。ACK が得られなければその割り当てを破棄し、クライアントは再度 Join できる。

## 状態遷移

### クライアント

```text
NotReady -- Join(id) --> Joining(id)
Joining(id) -- Master から一致する SetAddress --> Ready(id)
Ready(id) -- 再 Join --> Joining(id)
```

- Join の送信元は常に `0x00`、送信先は `0x01`。
- Joining 中は、自分の `id` と一致し、Master (`From=0x01`) から未割り当て宛てに届いた SetAddress だけを採用する。
- SetAddress の割り当て先が `0x02`–`0xFE` 以外なら拒否する。
- 割り当てを採用したらクライアントアドレスを更新し、Ready へ遷移して `Ack(0x00)` を送る。
- Ready 中に同じ `id` と同じアドレスの SetAddress を受けた場合は状態を変えず、同じ ACK を再送する。
- Join、SetAddress、ACK の `id`・宛先・送信元が一致しない場合は、別トランザクションとして混同しない。

### Master

```text
Join(id) -- 割り当て可能 --> pending assignment(id, address)
pending assignment -- Ack(0x00) --> 次の割り当て先へ進む
pending assignment -- 期限内に ACK なし --> 破棄
```

- Join は `From=0x00` である場合だけ割り当て対象とする。
- 割り当て先は `0x02` から順に選び、`0xFE` の次は枯渇として扱う。
- SetAddress の ACK は、ペイロード `0x00` と、割り当てたアドレスからの送信元を組み合わせて検証する。
- 保留がないときの `Ack(0x00)` は、完了済み SetAddress の重複 ACK として無視できる。その他の対象不明 ACK は Unexpected ACK とする。

## 妥当性検証

フレームを判定するときは、次の順序で論理的に確認する。

1. 境界を確認し、SOF/EOF をフレーム内部のデータとして数えない。
2. ESC の組を解除し、予約 byte の不正な生出現や不正な変換を拒否する。
3. ヘッダーの 16-bit little-endian ペイロード長と、解除後の実長を比較する。
4. Type が 0–6 のいずれかであることを確認する。
5. Type ごとの固定長・最大長を確認する。
6. 論理 byte 列の XOR チェックサムを確認する。
7. 宛先、送信元、ペイロード内容を現在の状態と照合する。
8. 不正フレーム、対象外フレーム、正当な重複フレームを別々に分類する。

典型的な拒否理由は、`InvalidChecksum`、未知の Type、`InvalidPayloadLength`、`FrameBufferTooSmall`、`InvalidEscapeSequence`、予約済みアドレスへの割り当てである。エラーの後は、後続の SOF から独立したフレームとして再解析する。

## 標準例

### Ping

`To=0x01`、`From=0x02`、Ping の論理内部列は次のとおり。

```text
01 02 00 00 00 03
```

`03` は `01 ^ 02`。ワイヤ上の完全なフレームは次のとおりで、予約 byte がないため追加のスタッフィングはない。

```text
FE 01 02 00 00 00 03 FF
```

### FE を含む Data

ペイロードに論理 `0xFE` が含まれる場合、ワイヤ上では `FD DE` になる。チェックサムは変換前の論理 `0xFE` を使って計算し、`FD` や `DE` を計算対象にしない。

## 分析時の回答規則

- まず「フレーミング」「アドレス」「種別・ペイロード」「ACK・状態」「エラー回復」のどの層の問題かを明示する。
- バイト列を扱う場合は、受信したワイヤ列、スタッフィング解除後の列、解釈結果を分けて示す。
- 長さとチェックサムは必ず論理列で再計算する。
- 宛先が違うだけのフレームを破損扱いせず、状態に合わない正しい形式のフレームと、形式自体が壊れたフレームを区別する。
- 仕様から導けないタイムアウト、順序、同時実行、再送回数などは断定せず、「未規定」と明示する。ただし上記の現行 SetAddress 再送上限 3 回はこのプロトコル契約として扱う。
- 仕様上の矛盾を見つけた場合は、該当するフィールド、状態、期待される動作、実際に起こる問題を短く対比する。
